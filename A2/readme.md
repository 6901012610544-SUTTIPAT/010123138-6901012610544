## 1. วัตถุประสงค์

- บันทึกรายการทางการเงินอย่างเป็นระบบ
- แยกประเภทรายรับ รายจ่ายประจำ รายจ่ายผันแปร และเงินออม
- แสดงรายการทั้งหมดและสรุปยอดเงิน
- ดูสรุปการเงินตามสัปดาห์และเดือน
- ฝึกประยุกต์ใช้ Encapsulation, Inheritance และ Polymorphism
- ฝึกอ่านและเขียนข้อมูลด้วยไฟล์ CSV

## 2. ความสามารถของโปรแกรม

| ความสามารถ | รายละเอียด |
| --- | --- |
| เพิ่มรายการ | เลือกประเภท ระบุรายละเอียด วันที่ และจำนวนเงิน |
| เลือกวันที่ | ใช้วันที่ปัจจุบันหรือกรอกวันที่เอง |
| แสดงรายการทั้งหมด | แสดงข้อมูลในรูปแบบตารางบน Terminal |
| สรุปผลการเงิน | แสดงรายรับ รายจ่ายแยกประเภท เงินออม และยอดคงเหลือ |
| รายงานรายสัปดาห์ | เลือกสัปดาห์ด้วยรูปแบบ `YYYY-W##` |
| รายงานรายเดือน | เลือกเดือนด้วยรูปแบบ `YYYY-MM` |
| บันทึกข้อมูล | จัดเก็บรายการลงไฟล์ CSV |
| ตรวจสอบข้อมูล | ตรวจวันที่ จำนวนเงิน และตัวเลือกเมนู |

## 3. ประเภทรายการ

| ประเภท | คลาส | ตัวอย่าง |
| --- | --- | --- |
| รายรับ | `IncomeTransaction` | เงินเดือน รายได้จากงานเสริม |
| รายจ่ายประจำ | `FixedExpenseTransaction` | ค่าเช่า ค่าสมาชิกรายเดือน |
| รายจ่ายผันแปร | `VariableExpenseTransaction` | ค่าอาหาร ค่าเดินทาง |
| เงินออม/ลงทุน | `SavingsTransaction` | เงินที่แยกไว้สำหรับออมหรือลงทุน |

### ความหมายของยอดคงเหลือ

ยอดคงเหลือหมายถึงเงินที่เหลือพร้อมใช้ หลังหักรายจ่ายและเงินที่แยกไปออม:

ยอดคงเหลือ = รายรับ − รายจ่ายประจำ − รายจ่ายผันแปร − เงินออม

เงินออมยังเป็นทรัพย์สินของผู้ใช้ ไม่ใช่ค่าใช้จ่ายที่สูญไป แต่ถูกหักออกจากยอดเงินพร้อมใช้

ควรตรวจสอบให้การทำงานของ `SavingsTransaction.get_balance_impact()` ตรงกับนิยามนี้ก่อนใช้งานจริง

## 8. การประยุกต์ใช้ OOP

### 8.1 Encapsulation — การห่อหุ้มข้อมูล

`BaseTransaction` เก็บข้อมูลสำคัญ เช่น วันที่และจำนวนเงินไว้ในแอตทริบิวต์ที่ขึ้นต้นด้วย `__` เช่น:

- `__date_string`
- `__amount`

การเข้าถึงหรือเปลี่ยนข้อมูลผ่าน Getter/Setter ช่วยรวมกฎการตรวจสอบไว้ในจุดเดียว เช่น จำนวนเงินต้องมากกว่า 0 และวันที่ต้องถูกต้อง

ใน Python การใช้ `__` ทำให้เกิด name mangling เพื่อลดการเข้าถึงหรือชนชื่อโดยไม่ตั้งใจ ไม่ใช่ระบบรักษาความลับของข้อมูล

### 8.2 Inheritance — การสืบทอด

รายการแต่ละประเภทสืบทอดจาก `BaseTransaction`:

```text
BaseTransaction
├── IncomeTransaction
├── FixedExpenseTransaction
├── VariableExpenseTransaction
└── SavingsTransaction
```

ข้อมูลและพฤติกรรมพื้นฐานใช้ร่วมกันได้ ส่วนพฤติกรรมเฉพาะประเภทกำหนดในคลาสลูก ทำให้ลดโค้ดซ้ำและดูแลโปรแกรมง่ายขึ้น

### 8.3 Polymorphism — การเรียกใช้งานผ่านอินเทอร์เฟซเดียวกัน

คลาสลูกกำหนดพฤติกรรมของเมธอด เช่น:

- `get_balance_impact()` คืนผลกระทบต่อยอดคงเหลือ
- `get_type_name()` คืนชื่อประเภทรายการ

`FinanceManager` จึงเรียกเมธอดเดียวกันกับรายการหลายประเภทได้ โดยให้แต่ละออบเจ็กต์จัดการพฤติกรรมของตัวเอง

ตัวอย่างเชิงแนวคิด ไม่ใช่โค้ดที่ยืนยันว่าตรงกับซอร์สจริง:

```python
balance = sum(
    transaction.get_balance_impact()
    for transaction in transactions
)
```

### 8.4 Factory Pattern — การรวมจุดสร้างออบเจ็กต์

`TransactionFactory` เลือกสร้างออบเจ็กต์ให้ตรงกับประเภทที่ระบุ

ตัวอย่างแนวคิด:
- ประเภทรายรับ → `IncomeTransaction`
- ประเภทรายจ่ายประจำ → `FixedExpenseTransaction`
- ประเภทรายจ่ายผันแปร → `VariableExpenseTransaction`
- ประเภทเงินออม → `SavingsTransaction`

ช่วยลดการกระจายเงื่อนไขสร้างออบเจ็กต์ไปหลายส่วนของโปรแกรม และสามารถนำมาใช้เมื่อสร้างรายการใหม่หรือแปลงข้อมูลจาก CSV กลับเป็นออบเจ็กต์ได้

## 11. แผนทดสอบโปรแกรม

ตารางนี้เป็นแผนทดสอบและผลที่คาดหวัง ยังไม่ใช่ผลยืนยันจากการรันจริง

| T05 | กรอกจำนวนเงินเป็น `abc` | แจ้งข้อผิดพลาดโดยไม่ทำให้โปรแกรมหยุด |

## 12. ข้อจำกัดและแนวทางพัฒนาต่อ

ส่วนนี้เป็นประเด็นที่ควรตรวจสอบหรือพัฒนาเพิ่มเติม ไม่ใช่รายการความสามารถที่ยืนยันว่ามีแล้ว

- ใช้ `Decimal` หรือเก็บเงินเป็นจำนวนเต็มหน่วยสตางค์ เพื่อลดปัญหาความคลาดเคลื่อนจาก `float`
- ปฏิเสธจำนวนเงินพิเศษ เช่น `NaN` และ `Infinity`
- เพิ่มการแก้ไขและลบรายการด้วยรหัสรายการที่ไม่ซ้ำกัน
- รองรับ CSV เสียหาย หัวตารางไม่ตรง หรือสิทธิ์เขียนไฟล์ไม่เพียงพอ
- เพิ่มระบบสำรองข้อมูลและการเขียนไฟล์อย่างปลอดภัย
- เพิ่ม Automated Tests สำหรับการตรวจข้อมูล การคำนวณ และการกรองช่วงเวลา
- แยกส่วน CLI ออกจากตรรกะทางการเงินเพื่อให้ทดสอบง่าย
- เปลี่ยนจาก CSV เป็น SQLite หากข้อมูลมีจำนวนมากหรือความสัมพันธ์ซับซ้อน
